# jig-essentials

jig-essentials is a collection of essential audio plugins in the Jig format. A Jig is a plugin
conforming to it: a dereferenceable IRI whose profile is RDF, whose processing is usually
WebAssembly, and whose user interface is either a generated panel or a skin. Everything runs
in the browser. This repository holds plugin source and built artefacts; it is not a host.
The reference host is Jiggy, in `~/github/jigdaw`.

The format is complete and normative. Read `~/github/jigdaw/README.agents.md` first, then
`~/github/jigdaw/docs/for-plugin-authors.md`, then `~/github/jigdaw/docs/plugin-profiles.md`
and section 3 of `~/github/jigdaw/docs/host-plugin-contract.md`. Where a guide and the
contract disagree, the contract governs. Where the contract and `vocabs/jigdaw.ttl` disagree,
the vocabulary is the defect.

`docs/plugins.md` in this repository is the backlog of plugins to build. Each heading there
is one plugin.

## What a plugin is here

A plugin lives in its own directory under `plugins/<name>/`, mirroring the layout in
`~/github/jigdaw/plugins/`. A typical directory contains:

- `profile.ttl`: the RDF profile, generated, never hand-edited for digests.
- `<name>-processor.js`: the AudioWorklet processor.
- `<name>.cpp` or `<name>.rs`: the DSP source, when WebAssembly is used.
- `<name>.wasm`: the built module.
- `build.sh`: builds the module and regenerates `profile.ttl`.
- `skin/`: optional SVG skin and its RDF bindings.
- `ui/`: optional `jig:ui` page.

`plugins/index.json` is the generated catalogue entry for the collection, if one is published.

## Non-negotiable real-time rules

These apply to every processor in this repository.

- Never allocate, touch the network or storage, log through an unbounded sink, or take an
  unpredictable lock inside `process()`.
- Never call `WebAssembly.Memory.grow()` from `process()`. It detaches every existing view on
  that memory, so a held `Float32Array` becomes zero-length and the symptom is silence
  rather than an exception.
- Preallocate every buffer before the processor reports ready. A processor that is not ready
  outputs silence; it does not throw and it is not audible.
- Anything that happens at a point in time is located by stream position, never by the index
  within the current block and never by equality with a block boundary.
- Treat plugin code as untrusted. Surface errors and isolate failures.

## RDF conventions

- One namespace of our own is not minted here. Jig terms are `http://purl.org/stuff/jigdaw/`,
  prefix `jig:`. Musical semantics are `trn:`, parameters are `lv2:` and `units:`, provenance
  is `prov:`. Reuse before inventing; a term general enough to belong to `trn:` is proposed
  upstream to the transmission repository rather than forked into `jig:`.
- No blank nodes for anything addressable. Skolemise as a fragment of the containing
  document's IRI.
- Model topology as explicit named arcs with named ports. Do not encode it as `rdf:List`.
- `profile.ttl` is generated by the build. Never write a `jig:integrity` digest by hand.
  Generate it with `bin/write-profile.js` from `~/github/jigdaw`, or every rebuild silently
  breaks the plugin.
- A profile with no `jig:module` is valid with a warning, which is correct for a plugin whose
  processing is plain JavaScript.

## Repository conventions

- ES modules throughout. Node 20 or later. npm. Scripts run from the repository root.
- Every source file opens with a path comment, as `// plugins/boost/boost-processor.js`.
- Comments describe intent where it is not obvious, or an unusual API. Not effects.
- Prefer deterministic offline audio tests over device-based ones. An `OfflineAudioContext`
  render is reproducible; a live context is not.
- A source file past about 400 lines is worth a look and past about 600 usually wants
  splitting, along a seam that already exists rather than by line count.

## Plugin authoring conventions

- Copy a plugin from `~/github/jigdaw/plugins/` that is close to yours. `boost` is the
  smallest in C++; `tremolo` has no WebAssembly.
- Name every parameter three times and consistently: in the profile, in the processor, and in
  the module. `tests/host/*.test.js` in the host binds them.
- A plugin that may cause aliasing artefacts should support optional oversampling, as noted
  in `docs/plugins.md`.
- A control nobody can use is left out, not shown disabled.
- Follow WCAG 2.2 at AA for any `jig:ui` or skin. A plugin author who ships no `jig:skin`
  gets the host's generated panel.

## Validating

Use the tools in `~/github/jigdaw`:

```sh
cd ~/github/jigdaw
npm run validate -- /path/to/profile.ttl   # SHACL shapes, exits non-zero on violation
npm run check-plugin -- <IRI>             # renders it headless: does it make sound
```

Syntax check with raptor where available:

```sh
rapper -i turtle -c profile.ttl
```

A plugin is not done until its profile validates and it renders sound in a headless check.

## Working rules

- API keys are sacred. They must not be shared, and nor may anything that merely looks like
  one be committed.
- Do not run any `git` operations unless the user explicitly approves them.
- Before creating a file, list the directory it is going into.
- Run the build after any change to a processor, module or profile. A command that exits 0
  having produced nothing is a failure.
- Log mistakes in `MISTAKES.md`, newest first: what happened, root cause, prevention, if
  this repository grows one.
